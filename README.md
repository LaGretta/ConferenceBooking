# Conference Room Booking API

Просте API для оренди конференц-залів: керування залами та послугами, пошук вільних залів на потрібний час і бронювання з автоматичним розрахунком вартості.

Написано на **.NET / ASP.NET Core Web API** з **Onion-архітектурою**, база — **SQL Server** через EF Core.

---

## Що вміє

- **Зали** — додати, редагувати, видалити, додати послугу до залу.
- **Пошук** — знайти вільні зали на заданий час і місткість.
- **Бронювання** — забронювати зал з обраними послугами; вартість рахується автоматично.
- **Розрахунок вартості** — погодинно, з урахуванням часу доби (див. нижче).

---

## Як рахується вартість

Вартість оренди = базова ставка залу × години, де кожна година має свій коефіцієнт залежно від часу доби:

| Час | Коефіцієнт |
|-----|-----------|
| Ранок (06:00–09:00) | −10% |
| Стандарт (09:00–18:00) | базова |
| Пік (12:00–14:00) | +15% |
| Вечір (18:00–23:00) | −20% |

Розрахунок **погодинний**: якщо бронювання перекриває кілька періодів (напр. 10:00–14:00), кожна година рахується за своїм коефіцієнтом. Пікова націнка (12:00–14:00) має пріоритет над стандартними годинами, бо це вужчий діапазон усередині них.

До вартості оренди додається сума обраних послуг.

> **Приклад:** Зал А (2000/год), 10:00–14:00, без послуг →
> 10–12 стандарт (2000×2) + 12–14 пік (2000×1.15×2) = **8600**

## Як запустити

**Потрібно:** .NET SDK, SQL Server.

1. Вкажіть рядок підключення в `ConferenceBooking.API/appsettings.json` (за замовчуванням локальний SQL Server):
   ```json
   "ConnectionStrings": {
     "DefaultConnection": "Server=localhost;Database=ConferenceBookingDb;Trusted_Connection=True;TrustServerCertificate=True;"
   }
   ```

2. Запустіть:
   ```
   dotnet run --project ConferenceBooking.API
   ```
   База створюється автоматично при першому старті (міграції + початкові дані: Зали А/B/C з послугами).

3. Відкрийте Swagger: `http://localhost:5067/swagger`

**Тести:**
```
dotnet test
```

## Основні ендпоінти

| Метод | Шлях | Опис |
|-------|------|------|
| POST | `/api/halls` | Додати зал (з послугами) |
| PUT | `/api/halls/{id}` | Редагувати зал |
| DELETE | `/api/halls/{id}` | Видалити зал |
| POST | `/api/halls/{id}/services` | Додати послугу до залу |
| POST | `/api/bookings/search` | Знайти вільні зали (час + місткість) |
| POST | `/api/bookings` | Забронювати зал (з розрахунком вартості) |

Приклади запитів зручно пробувати прямо у Swagger.

## Архітектура

Onion / Clean — залежності спрямовані до центру:

```
Domain          — сутності (Hall, RoomService, Booking, BookingServiceItem)
Application     — DTO, інтерфейси, сервіси, розрахунок вартості, валідатори, мапінг
Infrastructure  — EF Core, DbContext, репозиторії, Unit of Work
API             — контролери, Swagger, обробка помилок
Tests           — unit-тести
```

Логіка розрахунку винесена в окремий `PricingCalculator` — її легко читати й тестувати окремо.

## Технічні рішення

- **Розрахунок погодинно** — точно обробляє бронювання що перекривають кілька тарифних періодів.
- **Захист від подвійного бронювання** — перевірка перетину інтервалів; сама бронь виконується в транзакції. За дуже високої конкурентності надійніше було б застосувати рівень ізоляції Serializable або блокування на рівні БД — тут для простоти обмежився перевіркою в транзакції.
- **Валідація** — вхідні дані перевіряються (FluentValidation): додатні місткість/ціни, коректний час, не можна бронювати минуле чи зайнятий зал, не можна обрати послуги іншого залу.
- **Обробка помилок** — глобальний обробник повертає зрозумілі відповіді (404/400) у форматі ProblemDetails; внутрішні помилки не розкривають деталей назовні.
- **Транзакція** використовується там де вона має сенс (бронювання), а не всюди.

## Припущення

- Бронювання кратні цілій годині (розрахунок іде погодинно).
- Нічні години (23:00–06:00) у ТЗ не описані — застосовується базова ставка.
- Автентифікація не реалізована, бо ТЗ не передбачає користувачів. У продакшені API був би за шаром автентифікації — архітектура дозволяє додати це без змін бізнес-логіки.
